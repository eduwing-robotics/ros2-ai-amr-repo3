## 1. 이 문서의 목적

이 문서는 발표 PPT의 이동 서버 부분을 만들기 위한 사실 정본이다. 단순 기능 소개뿐 아니라 개발 과정에서 무엇이 실패했고, 원인을 어떻게 분리했으며, 어떤 대안을 폐기하거나 보류했는지까지 담는다.

발표에서는 다음 세 수준을 반드시 구분한다.

- `구현 완료`: 코드와 계약이 존재하고 자동 테스트를 통과한 상태
- `프리뷰 검증`: 실제 주행 없이 시나리오 전개 결과를 확인한 상태
- `실물 검증`: 로봇이 실제 환경에서 해당 구간 또는 전체 흐름을 수행한 상태

이 구분이 필요한 이유는 등록된 모든 경로가 시나리오로 생성된다는 사실과, 모든 조합이 실물 E2E로 검증됐다는 주장은 서로 다르기 때문이다.

## 2. 발표의 핵심 메시지

> Main의 업무 명령을 로봇별 물리 동작으로 안전하게 변환하고, Nav2·ArUco·리프트를 결합해 반복 가능한 물류 주행을 구현했다.

핵심 성과는 단순히 로봇이 한 번 움직였다는 것이 아니다.

1. Main은 위치 좌표나 마커 번호를 몰라도 업무 시나리오를 명령할 수 있다.
2. 이동 서버가 로봇별 좌표, 회전, 정밀 접근, 삽입 거리, 리프트 동작을 소유한다.
3. Nav2의 장거리 주행과 ArUco 기반 근거리 정렬을 분리해 정밀도를 높였다.
4. 실패를 즉시 성공으로 오인하지 않도록 준비 상태, 명령 수명주기, 콜백을 명시했다.
5. 로봇 2대는 ROS domain과 API 포트를 분리하고, 공용 구간은 교통 잠금으로 충돌 위험을 제어한다.

## 3. PPT 초안 검토 결과

초안 25장의 전체 구조는 `프로젝트 소개 → 시스템 설계 → 자율주행 → 비전 → 최종 결과`로 자연스럽다. 이동 서버에 직접 해당하는 슬라이드는 13~17장이고, 22~24장의 통합 결과에도 이동 서버 성과가 반영되어야 한다.

현재 초안의 장점:

- 하드웨어, API, Nav2, ArUco, 검증 순서가 이해하기 쉽다.
- Main과 이동 서버의 포트 및 ROS domain 분리가 드러난다.
- `Nav2 접근 → ArUco 정렬 → 삽입 → 리프트 → 후진` 흐름이 핵심을 잘 잡고 있다.

보강할 점:

- 최종 구조만 있고 실제 개발 과정의 문제 해결이 보이지 않는다.
- 로봇1과 로봇2의 검증 수준 차이가 드러나지 않는다.
- API 프리뷰 성공과 실물 E2E 성공이 섞일 가능성이 있다.
- 적용하지 않은 EKF, 중앙 Supervisor, 공용 costmap 같은 시도가 최종 기능처럼 오해될 수 있다.
- 18단계의 의미를 Main 업무 단계와 이동 서버 물리 단계로 나눠 설명해야 한다.

## 4. 개발 연혁

### 2026-06-27 — 이동 서버 구조 정리

- 하나의 큰 실행 스크립트를 `nav_app` 패키지의 router, service, runtime 구조로 분리했다.
- 문서를 as-built, design, reference, runbook, ADR로 나누고 기존 스크립트는 호환 진입점으로 유지했다.
- 이후 실물 문제를 API, Nav2, 비전, 리프트 단위로 분리해 진단할 기반을 만들었다.

### 2026-07-03 — 로봇2 기본 주행 스택 안정화

- 로봇2를 ROS domain 5, Movement API 8002, 전용 맵으로 분리했다.
- Nav2·AMCL, API, `leave_dock`, `move_to_point`, 카메라와 ArUco 연결을 단계적으로 검증했다.
- Rotation Shim 설정 형식 오류, 초기 pose 미설정, 속도 평활기의 과도한 감속, 좌우 진동, 느슨한 yaw 허용값을 수정했다.
- 비대화형 SSH에서 overlay와 `LDS_MODEL`이 누락되는 운영 문제도 실행 절차에 반영했다.

### 2026-07-04 — 카메라와 도킹 실패 원인 분리

- ROS 카메라가 libcamera/IPA ABI 충돌로 안정적으로 실행되지 않는 문제를 확인했다.
- Raspberry Pi 계열 libcamera/Picamera2 발행 방식으로 전환해 약 10Hz 영상을 확보했다.
- odom TF 유실로 AMCL pose가 비정상적으로 커지고 주행이 실패하는 현상을, bringup/localization 재기동 문제로 분리했다.
- 동일 timestamp 때문에 LMS가 이전 명령을 선택하던 문제를 `id DESC` 보조 정렬로 해결했다.

### 2026-07-05 — 로봇2 물류 시나리오 실물 성공

- 바닥 주행 가능 영역을 기반으로 waypoint를 만들고 실물 간섭을 반영해 보정했다.
- 모든 구역에 동일한 삽입 거리를 쓰지 않고 슬롯별 값으로 분리했다.
- 삽입 후 후진 거리가 설정값이 아니라 실제 삽입량을 사용하도록 수정했다.
- 접근 정렬과 실제 삽입 동작을 분리해 벽 압박과 시간 제한 실패를 줄였다.
- 로봇2에서 다음 실물 흐름을 성공시켰다.
  - 출고2 → 창고 A → 대기2
  - 입고1 → 창고 C → 대기2
  - 입고2 → 창고 B → 출고1 → 대기2

### 2026-07-06 — 리프트 연동 도입

- 기존의 리프트 no-op과 고정 대기를 실제 LiftClient 및 bridge로 교체했다.
- 작업 순서를 `삽입 → 리프트 → 후진`으로 명시했다.
- 43mm 수동 리프트 동작을 확인했으나, 이 시점의 전체 dock-transfer E2E는 추가 검증 대상으로 남았다.
- 상단 물리 limit가 없어 100mm 소프트 제한과 하단 homing을 안전 기준으로 사용했다.
- 리프트 통합이 안정화되기 전에는 두 로봇 동시 운행을 의도적으로 미뤘다.

## 5. 대표 문제와 해결

| 문제 | 원인 | 해결 | 결과 |
|---|---|---|---|
| Nav2 기동 후 주행 불가 | 초기 pose와 lifecycle 준비 미완료 | 시작 pose seed, lifecycle/readiness 확인 | 명령 전 준비 여부를 API가 판단 |
| 직선 주행 중 좌우 진동 | 매 주기 heading 회전, 과도한 감속 설정 | rotate once, OPEN_LOOP smoother | 좁은 구간 주행 안정화 |
| AMCL pose 비정상·계획 실패 | odom TF 유실 | bringup/localization 재기동 및 freshness 검사 | 원인 없는 재시도 대신 상태 복구 가능 |
| 카메라 실행 불안정 | libcamera/IPA ABI 충돌 | Picamera2 기반 발행 경로 사용 | ArUco 입력 약 10Hz 확보 |
| 벽 접촉·삽입 과다 | 전 구역 공통 거리와 yaw 오차 | 구역별 삽입 거리, 수직 정렬, 저속 삽입 | 여러 물류 구역 실물 성공 |
| 후진 거리 불일치 | 설정 거리 사용 및 잘못된 reverse 매핑 | 실제 삽입량 사용, slot reverse 분리 | 작업 후 원위치 복귀 가능 |
| ArUco 픽셀 기준 오차 | 원근·해상도에 따른 픽셀 폭 변동 | 카메라 보정 + metric distance | 거리 판단을 물리 단위로 통일 |
| Main과 로봇 튜닝 결합 | Main이 좌표·마커를 알아야 함 | Scenario API와 waypoint registry | Main 명령 변경 없이 로봇 튜닝 가능 |
| 접수와 완료 혼동 | 비동기 API 의미 불명확 | 202 접수, 상태 조회, callback 단계 분리 | 업무 진행 상태 추적 가능 |
| 두 로봇 충돌 위험 | 서로 다른 domain/planner가 상대를 모름 | 구간 lock과 409 재시도 계약 | 공용 구간 동시 진입 억제 |
| 로봇1 precision timeout | Nav2 approach 정지 좌우 오차 2.18cm | approach 정지 정확도와 ArUco 완료 조건을 분리 진단 | 거리 19.44cm 성공과 중앙/yaw 실패를 정확히 구분 |

## 6. 도입했다가 폐기하거나 보류한 접근

| 접근 | 결정 | 이유 |
|---|---|---|
| Main이 직접 x/y/yaw와 마커·삽입값 전송 | 폐기 | 업무 서버가 로봇 튜닝에 종속되고 변경 영향이 커짐 |
| 픽셀 폭을 최종 정지 거리로 사용 | 폐기 | 원근과 검출 변동으로 벽 접촉 위험이 남음 |
| 모든 위치에 동일한 삽입 거리 사용 | 폐기 | 구역별 벽·랙 구조와 카메라 오프셋이 다름 |
| CLOSED_LOOP velocity smoother | 기본값에서 제외 | 실물에서 0.12m/s 명령이 약 0.035m/s로 과도하게 감소 |
| EKF filtered odometry를 항상 사용 | 보류 | 일부 구간 개선과 일부 도킹 실패가 혼재해 기본 안정성이 낮음 |
| 중앙 Supervisor 단일 실행 | 현재 운영에서 제외 | 장애 원인이 가려지고 개별 프로세스 복구가 어려웠음 |
| 공용 costmap·중앙 다중 로봇 planner | MVP에서 제외 | 구현 복잡도 대비 발표 범위의 충돌 제어는 segment lock으로 충족 가능 |
| 실패 후 남은 단계 자동 강행 | 금지 | 실제 위치와 명령 authority가 불확실한 상태에서 2차 충돌 위험 발생 |

이러한 폐기 결정은 실패를 숨긴 내용이 아니라, 실물 안정성을 위해 복잡도를 줄인 설계 결과로 발표한다.

## 7. 최종 시스템 구조

```text
Main Server
  ├─ 업무 시나리오 요청 + command_id + callback
  ├─ tb3_1 → Movement API :8001 / ROS_DOMAIN_ID=2
  └─ tb3_2 → Movement API :8002 / ROS_DOMAIN_ID=5
                       │
                       ▼
               Movement Scenario API
  readiness gate → route/waypoint 전개 → 실행 상태 저장
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
       Nav2/AMCL   ArUco 정밀정렬   Lift bridge
     장거리 접근     근거리 도킹     상·하차 동작
          └────────────┼────────────┘
                       ▼
              TurtleBot3 실제 동작
                       │
                       ▼
         단계 callback / 결과 / 실패 원인
```

### 책임 분리

- Main은 ‘어디서 무엇을 어디로 옮길지’를 결정한다.
- 이동 서버는 ‘어떤 좌표와 센서 조건으로 안전하게 움직일지’를 결정한다.
- 로봇 차이는 waypoint, marker, 거리, lift profile에 격리한다.
- Main은 로봇별 내부 튜닝이 바뀌어도 동일한 형식으로 명령을 보낸다.

## 10. 두 로봇 동시 운행에 대한 정확한 설명

두 로봇은 domain과 API가 분리돼 명령 및 ROS topic 충돌은 방지된다. 그러나 이것만으로 물리 충돌까지 자동 방지되는 것은 아니다. 각 로봇의 Nav2 planner는 상대 로봇을 지속적으로 공유하는 중앙 planner가 아니다.

현재 충돌 제어 방식:

- 공용 구간 진입 전 segment lock 획득
- 다른 로봇이 보유하면 `409 WAITING_TRAFFIC`
- Main은 기존 command ID를 재사용하지 않고 새 command ID로 재시도
- 두 로봇의 home/대기 역할을 분리해 교차 동선을 줄임

발표 표현:

> 두 로봇의 통신·실행 환경을 분리하고, 공용 통로는 이동 서버의 구간 잠금과 Main의 재시도로 동시 진입을 제한하도록 설계했다.

피해야 할 표현:

> 두 로봇이 서로를 실시간 인식해 모든 상황에서 충돌을 자동 회피한다.

동일 aisle에서의 2대 실물 lock 검증은 아직 미완료이므로, 영상 촬영 전 별도의 안전요원과 비상정지 준비가 필요하다.

## 12. 현재 남은 문제와 발표 리스크

1. 로봇1은 전체 시나리오 E2E 완료로 표현하지 않는다.

7. 두 로봇이 서로를 센서 융합으로 완전 인식한다고 말하지 않는다.
8. 리프트 상단은 물리 limit가 아니라 소프트 제한이므로 안전 항목으로 명시한다.

## 14. 추가를 권장하는 한 장

제목: `실물 실패를 반복 가능한 시스템으로 바꾼 과정`

```text
초기: 좌표 직접 명령 + 공통 거리 + 픽셀 기준
  ↓
문제: 벽 접촉, marker 유실, 후진 불일치, 재기동 후 상태 유실
  ↓
개선: waypoint registry + metric ArUco + 실제 삽입량 후진
  ↓
제품화: Scenario API + readiness + callback + traffic lock
  ↓
결과: 로봇별 튜닝을 감춘 반복 가능한 물류 실행
```

이 한 장은 ‘기능을 조립했다’가 아니라 ‘실물 문제를 진단하고 시스템으로 해결했다’는 팀의 기술 역량을 가장 잘 보여준다.

## 16. 4분 발표 대본 초안

“저희 이동 서버의 역할은 Main이 보낸 업무 명령을 실제 로봇의 안전한 물리 동작으로 바꾸는 것입니다. Main은 입고 위치와 창고, 출고 위치 같은 업무 의미만 보내고, 좌표나 ArUco 번호, 접근 거리, 리프트 높이는 이동 서버가 관리합니다.

장거리 이동은 Nav2와 AMCL이 담당하고, 벽이나 랙 앞의 마지막 구간은 ArUco로 중앙, 방향, 거리를 맞춥니다. 이후 저속으로 삽입하고 리프트 작업을 수행한 뒤 실제 삽입한 거리만큼 후진합니다. 입고1처럼 회전 공간이 필요한 곳은 Main 명령을 바꾸지 않고 이동 서버가 pre-approach를 자동으로 추가합니다.

개발 과정에서는 카메라 ABI 충돌, odom TF 유실, 공통 삽입 거리로 인한 벽 접촉, 픽셀 기준 거리 오차, 후진 매핑 오류가 있었습니다. 이를 카메라 발행 경로 교체, readiness 검사, 구역별 보정, calibrated metric distance, 실제 삽입량 기반 후진으로 해결했습니다. EKF와 중앙 Supervisor도 시험했지만 실물 안정성과 복구 편의성이 낮아 현재 기본 운영에서는 제외했습니다.

로봇1과 로봇2는 각각 domain 2와 5, API 8001과 8002로 분리돼 있습니다. 공용 통로는 segment lock으로 동시에 진입하지 않도록 제어합니다. 로봇2는 대표 물류 E2E 흐름을 실물로 완주했고, 로봇1은 입고1·입고2·창고 A의 정밀 접근과 삽입 구간을 성공했습니다. 다만 로봇1 창고 B와 일부 approach 정확도, 두 로봇 동일 통로의 실물 검증은 남아 있어 발표에서도 구현 범위와 실물 검증 범위를 구분해 설명하겠습니다.”

## 18. 발표 전 최종 확인 순서

1. 코드 변경을 더 늘리지 않고 발표용 운영 기준선을 고정한다.
2. 로봇1 입고1 pre-approach 좌표를 무부하로 1회 검증한다.
3. 로봇2는 이미 검증된 대표 시나리오로 촬영한다.
4. 두 로봇 동시 영상은 공용 구간 lock을 먼저 저속 검증한 뒤 촬영한다.
5. 모든 영상에서 command ID, 시작·완료 callback, 로봇 번호가 식별되도록 한다.
6. PPT 문구는 이 문서의 검증 수준 표를 기준으로 확정한다.

## 20. 최종 결론

이동 서버의 최종 가치는 ‘로봇을 움직이는 API’에 그치지 않는다. Main의 업무 의미와 로봇의 물리 튜닝을 분리하고, 장거리 Nav2와 근거리 ArUco, 리프트, 실패 복구, 두 로봇 교통 제어를 하나의 실행 계약으로 묶은 것이 핵심이다.

발표에서는 성공 장면만 나열하기보다, 실물 문제를 계측하고 원인을 분리한 뒤 운영 가능한 구조로 바꾼 과정을 보여주는 편이 기술적 설득력이 높다. 동시에 아직 실물로 확인하지 않은 조합은 명확히 구분해야 최종 결과의 신뢰도가 올라간다.
