# 운영자/관리자 2계층 UI 분리

상태: Active
소유: Frontend
최종 갱신: 2026-06-22 14:25 KST
목적: UI를 운영자(매일 사용)와 관리자(시스템 정의) 두 계층으로 나누는 기준과 동작 단위 경계를 고정한다.

## Decision

UI를 추상화 레벨이 다른 두 계층으로 명확히 분리한다. 둘을 한 줄의 평평한
네비게이션에 섞지 않는다.

- 운영자 계층: "무엇을" 만 표현한다. 좌표, 스텝 순서, 슬롯 배정 로직을 보지 않는다.
- 관리자 계층: "어떻게" 를 정의한다. 좌표, 구역, 슬롯, 스텝, 동작 정의, DB를 다룬다.

운영자의 입출고 명령은 항상 `POST /work-orders` 한 경로로만 들어가고, 시나리오는
서버가 관리자 정의 데이터(구역·슬롯·시나리오 템플릿)로 자동 합성한다. 운영자 UI는
`/tasks`, `/scenario-presets`, `/missions` 를 직접 조합하지 않는다.

### 네비게이션 구조

최상단을 5개 평평한 area 대신 `운영` / `관리` 모드 토글로 둔다. (인증은 추후;
초기에는 단순 모드 전환.)

```text
[ 운영 ] [ 관리 ]
 ├ 관제 대시보드/캠/수동조작 ├ 맵 & 구역 waypoint CRUD
 ├ 입출고 품목+수량 → work order ├ 시나리오 preset 템플릿 + 테스트 실행
 └ 작업 task 목록/스케줄/상태 ├ 동작 정의 action_type + 파라미터
 ├ 슬롯·재고·품목 work_orders 의존 마스터
 ├ 로봇/카메라
 └ 시스템 통신로그/DB/설정/ESTOP
```

기록(이동기록·작업기록)은 양쪽에서 접근 가능한 별도 묶음으로 둔다. 운영자는 읽기,
관리자는 전부.

### 동작 단위 경계 ("여기까지 이동 → 리프트 들고 → 후진")

의미 동작(semantic action)은 LMS가, 모션 프리미티브(motion primitive)는 Movement
서버가 소유한다.

- LMS 관리자는 `pickup` 같은 의미 동작과 그 파라미터(`lift_height`,
 `approach_offset`, `reverse_distance` 등)만 정의/튜닝한다.
- "리프트 들고 후진" 실제 시퀀스는 Movement 서버가 `pickup` 을 받아 펼친다.
- 현재 `MissionStep.params` 구조와 일치하며, 로봇 제어 로직을 LMS에 중복하지 않는다.

따라서 "동작 정의" 관리자 화면은 모션 시퀀스 편집기가 아니라 action_type 목록 +
파라미터 스키마 편집기다(현 `frontend/web/src/features/scenario/constants.ts` 의
`ACTION_PARAMS` 를 DB화).

## Context

- 백엔드 `backend/app/services/work_orders.py` 는 이미 "운영자=고수준 의도" 구조다.
 품목+수량+입출고를 받아 구역·슬롯으로 시나리오를 자동 합성한다(`_compose_scenario`).
 슬롯/재고 DB·API 는 대부분 구현됨.
- 그러나 프론트가 못 따라간다:
 - 운영자가 `work_orders` 를 호출하는 입출고 화면이 없다. `TaskCreate` 는 여전히
 preset 을 고르는 반관리자 화면이다.
 - `work_orders` 가 필수 의존하는 슬롯/재고/품목 **관리자 화면이 통째로 없다**
 (`system/*` 에 robots/cameras/commlogs/dbtables 뿐). 이것이 "관리자 작업이
 빈약"한 1순위 원인.
- 네비게이션은 `app/menus.ts` 에서 5개 area 가 평평하게 섞여 역할 구분이 없다.
- 동작 정의가 `constants.ts` 에 하드코딩되어 관리자가 다룰 수 없다.

## Consequences

- 운영자 입출고 화면과 슬롯/재고/품목 관리 화면 두 개를 채우면 "관리자 빈약 +
 운영자 추상화" 문제가 동시에 풀린다.
- 권장 구현 순서:
 1. 슬롯·재고·품목 관리 UI (입출고 자동화를 실제로 켜는 전제, 1순위)
 2. 운영자 입출고 화면 (`work_orders` API 호출; 백엔드 완성됨)
 3. 네비게이션 운영/관리 모드 분리
 4. 동작 정의 화면 (`ACTION_PARAMS` DB화)
 5. (선택) 역할 인증
- 빌드 단계·완료 기준은 에서 관리한다. 본 문서는 그 위의 UI 계층 분리 원칙만 고정한다.
- 모션 프리미티브는 Movement 서버 책임으로 고정되므로, "리프트/후진" 세부 동작을
 LMS 시나리오 에디터에서 편집하자는 요구는 파라미터 노출로 대응하고 시퀀스 편집은
 도입하지 않는다.
