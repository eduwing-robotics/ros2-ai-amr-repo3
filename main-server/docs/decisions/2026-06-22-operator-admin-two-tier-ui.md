# 운영자/관리자 2계층 UI 분리

- 상태: Implemented
- 소유: Frontend
- 작성: 2026-06-22
- 최종 갱신: 2026-07-28
목적: 일상 운영과 시스템 정의를 서로 다른 UI 계층으로 제공하고, 운영 요청의 추상화 수준을 고정한다.

## Context

운영 작업과 시스템 설정이 같은 탐색 계층에 섞이면 운영자가 좌표, 시나리오 단계와 장치 설정 같은 내부 정보를 직접 다루게 된다. 또한 입·출고 요청이 저수준 task나 preset 조합으로 노출되면 Main Server의 검증·계획 책임을 우회할 수 있다.

## Decision

UI를 목적이 다른 두 모드로 구분한다.

| 모드 | 사용자 질문 | 제공 기능 |
| --- | --- | --- |
| 운영 | 지금 어떤 작업을 실행하고 어떻게 복구할 것인가 | 관제, 입·출고, 작업, 재고와 이벤트 |
| 관리 | 작업에 사용할 기준정보와 장치를 어떻게 정의할 것인가 | 맵·구역, 슬롯·품목, 로봇·카메라와 시스템 설정 |

기록은 운영과 관리 양쪽의 결과를 확인하는 공통 영역으로 둔다.

운영자의 입·출고 요청은 품목, 수량과 작업 의도만 전달한다. Main Server가 현재 재고·위치·로봇 상태를 재검증하고 실행 단계를 구성하며, 브라우저가 좌표나 원자 명령을 직접 조합하지 않는다.

## Action Boundary

의미 동작은 Main Server가, 모션 프리미티브는 Nav Server가 소유한다.

- Main Server는 `move_to_point`, `dock_transfer`, `aruco_align`, `leave_dock` 같은 업무 단계와 파라미터를 선택한다.
- Nav Server는 주행, 정렬, 리프트와 이탈의 물리 실행을 담당한다.
- 운영 UI는 작업 의도와 복구 선택지를 제공하고 모션 시퀀스 편집기로 동작하지 않는다.

## Implemented Result

- `frontend/web/src/app/menus.ts`가 운영·관리 모드와 공통 기록 목적지를 정의한다.
- `frontend/web/src/routes/registry.ts`가 운영, 관리와 기록 화면을 명시적으로 연결한다.
- 운영 화면은 관제·입출고·작업·재고·이벤트를 제공한다.
- 관리 화면은 맵·구역, 슬롯·재고·품목, 로봇·카메라와 시스템 진단을 제공한다.
- 화면 변경 후에는 Backend가 확정한 상태를 다시 조회하며 브라우저의 임시 상태를 업무 정본으로 사용하지 않는다.

현재 모드 분리는 정보 구조와 작업 범위의 구분이다. 사용자 인증과 권한 부여 정책은 별도 보안 결정으로 다룬다.

## Stable Rules

1. 운영 화면에 좌표·DB row·원자 명령 편집을 노출하지 않는다.
2. 관리 화면의 변경도 Main API 검증과 PostgreSQL transaction을 거친다.
3. 브라우저는 Nav·AI·DB에 직접 연결하지 않는다.
4. 신규 화면은 운영 의도인지 시스템 정의인지 먼저 결정한 뒤 해당 모드에 배치한다.
